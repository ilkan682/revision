Même pattern exact que les étudiants. Pas de photo, pas de detail(). La PK est un int auto (id_enseignant) au lieu d'une string.

Q

Comment tu as créé la base de données et l'utilisateur ?

Je me suis connecté à MySQL avec root sur la VM Hussain : mysql -u root -p. Ensuite j'ai créé la base : CREATE DATABASE `gestion-notes` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;. Q

Pourquoi 'ilkan'@'%' et pas 'ilkan'@'localhost' ?

Parce que dans notre architecture, Django et MySQL sont sur deux machines différentes. Le % signifie "connexion acceptée depuis n'importe quelle adresse IP". Si j'avais mis localhost, seules les connexions depuis la machine MySQL elle-même seraient acceptées, et Django qui tourne sur une autre VM ne pourrait pas se connecter. C'est directement lié au HOST: 'serveur-notes' dans settings.py.
Q

Montre la structure de la table etudiants — que donne DESCRIBE etudiants ?

DESCRIBE etudiants; retourne :

• numero_etudiant — varchar(20) — NOT NULL — PRI (clé primaire, car primary_key=True dans le modèle)
• nom — varchar(100) — NOT NULL
• prenom — varchar(100) — NOT NULL
• groupe — varchar(20) — NOT NULL
• email — varchar(254) — NOT NULL — UNI (index unique, car unique=True)
• photo — varchar(100) — YES (peut être NULL, car null=True dans le modèle). C'est le chemin du fichier, pas le fichier lui-même.
Q

Quelle est la différence entre DESCRIBE et SHOW CREATE TABLE ?

DESCRIBE donne une vue tabulaire simple : nom de colonne, type, nullable, clé, valeur par défaut. C'est lisible rapidement. SHOW CREATE TABLE retourne le SQL complet qui a été utilisé pour créer la table : on voit les contraintes complètes (CONSTRAINT name UNIQUE KEY...), les FK avec ON DELETE CASCADE, le ENGINE=InnoDB, le charset. C'est plus verbeux mais plus complet pour comprendre toutes les contraintes.
Q

Qu'est-ce que Django crée comme tables en plus des tiennes ?

Après python manage.py migrate, Django crée des tables système en plus des nôtres :

• django_migrations : historique de toutes les migrations appliquées
• django_content_type : référence tous les modèles (utile pour les permissions)
• auth_user, auth_group, auth_permission : système d'authentification Django
• django_session : sessions utilisateurs (messages flash, authentification)

Et nos tables à nous : etudiants, enseignants, ue, ressources, examens, notes.
Q

Pourquoi utf8mb4 et pas juste utf8 ?

En MySQL, utf8 est en réalité un encodage tronqué qui supporte seulement 3 octets par caractère. Or certains caractères Unicode (notamment les emojis comme 😀, mais aussi certains caractères asiatiques) nécessitent 4 octets. utf8mb4 (mb4 = multi-byte 4) est le vrai UTF-8 complet qui supporte tous les caractères Unicode. Utiliser utf8 peut provoquer des erreurs ou tronquer des données si un étudiant met un emoji dans son nom par exemple.
Q

Quelle est la différence entre DELETE et TRUNCATE ?

DELETE FROM table WHERE condition supprime des lignes spécifiques, avec log transaction par transaction. Si pas de WHERE : supprime tout mais lentement. TRUNCATE TABLE vide la table entière d'un coup, sans log ligne par ligne → beaucoup plus rapide. TRUNCATE remet aussi les compteurs AUTO_INCREMENT à 0. La différence importante : TRUNCATE ne peut pas être filtré (pas de WHERE), et il peut être bloqué par des FK. DELETE peut être rollbacké dans une transaction, TRUNCATE non (dans certains moteurs).

Questions Django probables du prof

Clique sur chaque question pour voir la réponse.

Q

C'est quoi get_object_or_404 ? Pourquoi tu l'utilises ?

C'est une fonction Django qui cherche un objet en base. Si il existe, elle le retourne. Si il n'existe pas (ex: l'URL /etudiants/99999/ mais cet étudiant n'est pas en base), elle renvoie automatiquement une réponse HTTP 404. Ça évite d'avoir un try/except ou un crash du serveur. Sans ça, Etudiant.objects.get(pk=pk) lancerait une exception DoesNotExist qui planterait la page avec une erreur 500.
Q

Pourquoi blank=True, null=True sur le champ photo ?

blank=True dit que le champ est optionnel dans les formulaires Django (validation). null=True dit que la colonne peut stocker NULL en base SQL. Les deux sont nécessaires : sans blank=True le formulaire refuserait qu'on soumette sans photo. Sans null=True Django mettrait une chaîne vide "" en base, ce qui est problématique pour un champ fichier.
Q

Explique le Q() dans la recherche.

Q() permet de construire des conditions SQL complexes avec OR et AND. Normalement filter() ne fait que du AND. Avec Q(nom__icontains=x) | Q(prenom__icontains=x) on fait : WHERE nom LIKE '%x%' OR prenom LIKE '%x%'. Le | = OR, le & = AND. Le __icontains = LIKE insensible à la casse.
Q

Pourquoi la suppression se fait sur POST et pas sur GET ?

Si on supprimait sur GET (simple lien), n'importe qui pourrait supprimer des données juste en visitant une URL. Un robot qui crawle le site, un utilisateur qui partage le lien, ou même Google qui indexe la page pourraient déclencher des suppressions. POST = action intentionnelle de l'utilisateur via un formulaire. C'est une règle de sécurité web de base : GET = lecture, POST/PUT/DELETE = modification.
Q

C'est quoi la différence entre instance=etudiant et pas d'instance ?

Sans instance : EtudiantForm(request.POST) = Django crée un nouvel objet en base (INSERT). Le formulaire est vide au départ. Avec instance=etudiant : EtudiantForm(request.POST, instance=etudiant) = Django modifie l'objet existant (UPDATE). Le formulaire est pré-rempli avec les valeurs actuelles. C'est la seule vraie différence entre creer() et modifier().
Q

Pourquoi enctype="multipart/form-data" ?

C'est un attribut HTML obligatoire pour envoyer des fichiers via un formulaire. Par défaut un formulaire envoie les données encodées en URL (texte). Avec multipart/form-data, le navigateur encode les fichiers binaires (photos) et les envoie en plusieurs parties. Sans ça, request.FILES serait vide côté Django, la photo ne serait jamais reçue.
Q

C'est quoi {% csrf_token %} ?

Protection contre les attaques CSRF (Cross-Site Request Forgery). Django génère un token secret unique par session et l'intègre dans chaque formulaire. Quand le formulaire est soumis, Django vérifie que le token correspond. Si un site malveillant essaie de soumettre un formulaire à ta place, il ne connaît pas le token → Django rejette la requête. Sans {% csrf_token %}, Django retourne une erreur 403 Forbidden sur tous les formulaires POST.
Q

Pourquoi la PK des étudiants est une string et celle des enseignants un int ?

Pour les étudiants : on utilise le vrai numéro étudiant comme identifiant (ex: "22015487"). C'est un CharField, donc <str:pk> dans les URLs. Pour les enseignants : il n'y a pas de numéro identifiant naturel, donc on laisse Django créer un id auto-incrémenté (1, 2, 3...). C'est un AutoField entier, donc <int:pk> dans les URLs. C'est pour ça que les deux fichiers d'URLs ont des types différents.
Q

C'est quoi le HOST 'serveur-notes' dans settings.py ?

"serveur-notes" est le nom DNS de la machine où tourne MySQL sur le réseau. Django (application web) est sur une machine, la base de données MySQL est sur une autre machine (celle de Hussain). C'est ce qu'on appelle une architecture avec service web et DB séparés. Django se connecte à MySQL via le réseau sur le port 3306, comme si c'était un serveur distant.
Q

C'est quoi les migrations ?

Les migrations sont des fichiers Python générés par Django (python manage.py makemigrations) qui décrivent les changements de la structure de la base de données. python manage.py migrate les applique : il crée ou modifie les tables SQL en fonction des modèles Python. C'est comme un historique de versions pour le schéma de la base. Le fichier 0001_initial.py dans le projet crée toutes les tables au premier lancement.
